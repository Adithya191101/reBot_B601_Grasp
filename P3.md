## What changed from P2

P2 lifted the object by sweeping seven **joint** deltas and measuring which one
went up. P3 replaces that with the demo's own five calls, on the demo's own IK:

```python
arm.get_tcp_pose()                              # measured jaw midpoint, base frame
arm.move_to_traj(x, y, z, rx, ry, rz, duration) # Cartesian -> Pinocchio IK -> drives
arm.open_gripper(distance_m)
arm.grasp(force)
arm.release_gripper()
```

The lift is now the instruction *"move the TCP 65 mm up"*, solved by
`solve_ik_with_retry` from the pinned `reBotArm_control_py` — the same library
`grasp_driver.py:136` imports. No joint waypoints, no sweep.

## The TCP had to be calibrated, not trusted

Pinocchio FK on the DM URDF and the shipped USD **disagree**. Measured across four
spread arm poses, the offset from `gripper_link` FK to the simulated jaw midpoint is:

```
mean offset (EE frame):  [-41.763, 0.008, 3.427] mm
max deviation from mean:   0.583 mm
```

The −41.76 mm in x is expected — it is the authored `gripper_link → finger origin`
translation (`-0.042091`). **The 3.4 mm in z is a genuine URDF↔USD discrepancy.**

Both DM URDFs (`reBotArmController_ROS2` and `reBot-Isaacsim`) produce
**byte-identical FK**, so this is *not* the unresolved π gripper-mount question —
that rotation leaves the jaw midpoint invariant. It is the shipped USD's
kinematics differing from the URDF's by 3.4 mm.

Because the deviation across poses is only 0.58 mm, it is a **constant frame
offset** and is correctable — the script asserts this rather than assuming it. A
pose-dependent residual would have meant the two models are genuinely different
kinematics, and the script fails if it ever becomes so.

## Three real defects found

**1. The SDK's package import pulls in CAN hardware.**
`reBotArm_control_py/__init__.py` imports `actuator`, which imports `motorbridge`
— the CAN driver. It is neither installable nor meaningful in simulation, and it
is not needed: the kinematics subpackage depends only on numpy and pinocchio.
Worked around by registering a stub parent package so the real `__init__` never
runs. No IK code is bypassed.

**2. `solve_ik_with_retry` cannot take a truncated seed.**
Unlike `solve_ik`, it has no `controlled_joints` parameter, yet does
`q_seed[:] = best.q` with a full-width result — so a 6-vector seed on this 8-DOF
model raises `could not broadcast (8,) into (6,)`. Fixed by seeding all 8. The two
finger joints are *downstream* of the `gripper_link` EE frame, so their Jacobian
columns are zero and IK cannot move them to reach a target.

**3. My own `move_to_traj` ignored `duration`.**
It routed through `probe._step_target`, which ramps over a fixed `RAMP_SECONDS`.
The vendor signature promises `duration`, so the argument was silently dead.
Replaced with a smoothstep ramp that honours it — which mattered physically, not
just cosmetically (below).

## Slip is reported, not engineered away

The first passing-looking attempt lifted the TCP 65 mm and the object only
**40.1 mm** — a 25 mm slip. The tempting fix is to command a taller lift until the
object clears 50 mm. That would have passed the gate while hiding a bad grasp.

Slip is a normal-force problem, so the fix was to squeeze harder (3.5 → 6.0 mm
past contact) and ramp the lift over 4 s instead of 1.5 s. Slip fell to **6.4 mm**,
and it is now an explicit scored check with the object rise reported against the
TCP rise, so a future regression cannot be masked by a bigger commanded move.

That P2's 3.5 mm squeeze held with zero drift under a joint-space lift, but slipped
under a Cartesian one, is itself the finding: the Cartesian path moves the tool
through a different configuration and loads the grasp differently.

## What P3 does and does not establish

**Does:** the arm is now commanded the way the demo commands it — Cartesian TCP
poses through Pinocchio IK — and the same contact-based pick succeeds, with
sub-millimetre Cartesian accuracy.

**Does not:** the target poses still come from `get_tcp_pose()` plus a hand-written
delta, and the object is still placed at the measured jaw. There is no
hand-eye calibration (**P3b**) and no perception (**P4**). It does not pick itself yet.
